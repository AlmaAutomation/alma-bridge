# Alma Bridge v1.2 — Work Plan (Phases 2–10)

**Status:** Phase 1 Architecture Audit output — a proposed plan. **No code changes are part of this document.**
**Basis:** findings in [ARCHITECTURE_REPORT](./ARCHITECTURE_REPORT.md), [IMPORT_GRAPH](./IMPORT_GRAPH.md), [READ_ONLY_BOUNDARIES](./READ_ONLY_BOUNDARIES.md).
**Guiding constraint:** freeze feature expansion; do not add new intelligence subsystems; preserve ADR-001 execution authority and the read-only boundary at every step.

Effort key: S ≤ 5 dev-days, M 5–10, L 10–20.

## Phase 2 — API modularization

- **Goals:** eliminate the 1,255-line `api/routes.py` monolith (risk R3); make each domain independently reviewable; remove function-local imports used only to dodge cycles (TD8).
- **Proposed changes:** split `routes.py` into tag-scoped routers mirroring the existing read-only routers: `bridge_routes.py`, `compliance_routes.py`, `modernization_routes.py`, `automation_routes.py`, `operator_routes.py`, `container_routes.py`, `system_routes.py`. Keep a thin aggregator that `include_router`s all of them.
- **Files likely touched:** `alma_bridge/api/routes.py` (shrinks to aggregator), new `alma_bridge/api/*_routes.py`, `alma_bridge/main.py` (unchanged include), tests referencing `alma_bridge.api.routes` symbols (`orchestrator`, `tls_modernizer`).
- **Risks:** moving module-level singletons (`orchestrator`, `tls_modernizer`, `_run_tasks`) can break import order or duplicate instances; tests import these directly.
- **Tests needed:** existing route tests must pass unchanged; add a test asserting the aggregator mounts every expected path prefix; keep OpenAPI path set snapshot to prove no endpoint moved/renamed.
- **Dependencies:** Phase 1.

## Phase 3 — Read-only boundary hardening + evidence-tier de-dup

- **Goals:** close guard gaps (R4), remove the read→core predicate edge (R6), de-duplicate errors/adapters/provenance (TD1, TD2, TD4).
- **Proposed changes:**
  1. Add `tests/_boundaries.py` with one shared `FORBIDDEN_IMPORT_FRAGMENTS` extended with `planner`, `remediation`, `execution.`, `automation`, `operator`; refactor all `test_*architecture_boundaries.py` to use it; add a meta-test asserting every read-only package is covered.
  2. Relocate `aggregate_verification_passed` (and siblings) from `session/stop_on_success_verification.py` to a neutral leaf (e.g. `alma_bridge/evidence/verification_semantics.py`); re-import from both `session` and the read-only tier.
  3. Introduce a shared `evidence/errors.py` base for `*NotFoundError` / `Malformed*`; collapse `ReadOnly*EvidenceAdapter` to one class + `Protocol`s; unify `EvidenceReference` and make `_to_knowledge_ref` public.
- **Files likely touched:** `session/stop_on_success_verification.py`, `knowledge/aggregation.py`, `comparison/queries.py`, `*/models.py`, `*/repository.py`, `intelligence/evidence.py`, all boundary tests.
- **Risks:** relocating the predicate touches the write path (orchestrator/verification) — must preserve behavior exactly; error-type unification can change exception identity used in `except` clauses and API status mapping.
- **Tests needed:** all boundary tests (extended); `test_verification_authority.py`, `test_stop_on_success_*` must be green; API error-status regression tests (404/422 shape unchanged).
- **Dependencies:** Phase 1 (safe after Phase 10 gates exist).

## Phase 4 — Persistence / repository layer

- **Goals:** one owner of SQLite connections and schema (R1); remove `_connect()` private access (TD5); enable transactional integrity, backups, and observability.
- **Proposed changes:** create `alma_bridge/storage/db.py` (connection factory, pragmas, migration runner) and per-aggregate repositories (`SessionRepository`, `AttemptRepository`, `ProfileRepository`, …) exposing read + write methods. Read-only tier depends only on read interfaces. Consolidate migration definitions currently scattered as `_SESSION_COLUMN_MIGRATIONS` etc.
- **Files likely touched:** `storage/outcomes.py` (decomposed), `intelligence/repository.py`, `compatibility/profile_store.py` + shadow/validation stores, `automation/*`, `compliance/learning.py`, `learning/*`.
- **Risks:** highest-blast-radius phase; concurrent-write semantics and existing on-disk DBs must migrate cleanly; many call sites.
- **Tests needed:** migration idempotency test on a copied real `outcomes.db`; concurrency/locking test; every store's existing tests; read-only adapters return identical data.
- **Dependencies:** Phase 3 (shared interfaces/errors first).

## Phase 5 — Core cycle decoupling

- **Goals:** reduce the 11 mutual import cycles (R2); make startup order explicit; remove function-local import workarounds.
- **Proposed changes:** extract shared leaf modules (domain types, prefix/runtime constants, verification semantics from Phase 3, hardware primitives) so `execution`/`session`/`bridge`/`learning`/`compatibility`/`compliance`/`automation` depend on leaves rather than each other. Introduce interfaces where a cycle is behavioral (e.g. orchestrator ↔ session via a protocol).
- **Files likely touched:** `execution/*`, `session/*`, `bridge/*`, `learning/*`, `compatibility/*`, `compliance/*`, `automation/*`, `validation/*`.
- **Risks:** subtle behavior change in the execution loop; large diff; must not weaken ADR-001 authority.
- **Tests needed:** a CI check that counts mutual cycles and asserts a monotonic decrease; full core suite (`test_orchestrator_*`, `test_session_*`, `test_verification_*`).
- **Dependencies:** Phase 4.

## Phase 6 — Application-identity key

- **Goals:** replace `file_hash`-equality correlation with a stable program-identity key (R8) so Advisor/Catalog/Comparison correlate the same app across versions/paths.
- **Proposed changes:** define an identity function (hash + PE metadata + name) and persist it on sessions; add a read index; keep `file_hash` as fallback.
- **Files likely touched:** `bridge/profile_builder.py`, `storage` schema (via Phase-4 migrations), `intelligence/repository.py`, `catalog/*`, `comparison/*`.
- **Risks:** identity definition churn; backfilling historical rows.
- **Tests needed:** identity determinism; correlation across two versions of one app; no regression when identity absent.
- **Dependencies:** Phase 4.

## Phase 7 — Planner convergence

- **Goals:** wire `CompatibilityBridgePlan` (`schemas/bridge_domain.py`) as the orchestrator's input, converging the split planner implementations (TD6, platform-direction "Planner as center").
- **Proposed changes:** make `DefaultCompatibilityPlanner` (or successor) produce a full `CompatibilityBridgePlan`; adapt `BridgeOrchestrator` to consume it; shrink ad-hoc orchestrator branches.
- **Files likely touched:** `session/services/planner.py`, `compatibility/planner.py`, `learning/orchestrator.py`, `schemas/bridge_domain.py`, `bridge/gap_analyzer.py`.
- **Risks:** touches the execution core directly; regression risk to verified-launch behavior (Code::Blocks path).
- **Tests needed:** `test_planner_adapter.py`, `test_orchestrator_*`, end-to-end verified-launch regression on the Code::Blocks fixture.
- **Dependencies:** Phase 5 (decoupled core).

## Phase 8 — Plugin architecture (**design only**)

- **Goals:** produce a design (no implementation) for a plugin registry enabling framework detectors, installers, launch planners, and verifiers to register without editing `orchestrator.py` (platform-direction "Expand plugin boundaries"). Migrate app-specific legacy branches (Ascension) off the core (TD7) — as a design target.
- **Proposed changes:** design document only. See [plugin-architecture.md](./plugin-architecture.md) stub.
- **Files likely touched:** docs only in v1.2.
- **Risks:** none (design).
- **Tests needed:** none (design); define acceptance criteria for a future implementation phase.
- **Dependencies:** Phases 5 and 7 (a decoupled core + converged planner make the plugin contract tractable).

## Phase 9 — Security, observability & deployment hardening

- **Goals:** address open-by-default auth and hardcoded CORS (R5); make the many stores observable as one system.
- **Proposed changes:** require API key (or explicit opt-out) for mutating endpoints when bound to non-loopback; move CORS origins to config; add DB/health metrics to `observability/prometheus.py`; document deployment posture.
- **Files likely touched:** `api/auth.py`, `main.py`, `config.py`, `observability/prometheus.py`, `SECURITY.md`.
- **Risks:** could break existing local dev workflows if defaults change — gate behind config with safe local default.
- **Tests needed:** `test_auth.py` extended; CORS config test; metrics smoke test.
- **Dependencies:** Phase 2.

## Phase 10 — Test-isolation & CI architecture gates

- **Goals:** resolve isolation debt (R7); make the architecture self-defending in CI.
- **Proposed changes:** fix shared-DB bleed (per-test `tmp_path` DBs everywhere, mirror the advisor boundary-test fixture); wire `scripts/find_polluters.py` into CI; add CI jobs for (a) shared boundary meta-test, (b) mutual-cycle count check, (c) OpenAPI path snapshot.
- **Files likely touched:** `tests/conftest.py`, `tests/test_suite_isolation.py`, `.github/workflows/ci.yml`, `scripts/find_polluters.py`.
- **Risks:** flushing out latent order-dependent test failures (that is the point).
- **Tests needed:** the gates themselves; a clean full-suite run in randomized order.
- **Dependencies:** Phases 2 and 3 (so the gates check the new structure).

---

## Cross-phase invariants (must hold at every step)

1. ADR-001 execution authority unchanged — only `session/verification_gateway.py` declares success.
2. Read-only tier never gains an execution/orchestrator/mutation import (guarded by Phase-3 tests).
3. No new intelligence subsystem is added (feature freeze).
4. Every phase ships with green boundary tests and the Code::Blocks verified-launch regression intact.
