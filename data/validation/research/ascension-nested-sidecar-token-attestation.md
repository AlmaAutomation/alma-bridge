## Sidecar PID/name guard behavior

From `AscensionClientServices.real.exe` strings and supplementary Wine probes:

1. `OpenProcess` on `--launcher-pid`
2. Process existence check
3. `Process32FirstW` / `Process32NextW`
4. Name validation — `"launcher PID does not belong to the launcher, exiting"`
5. Expected basename includes `ascension launcher.exe`

**Wine observation:** Alma decoy at `resources/alma-guard/Ascension Launcher.exe` appears in `tasklist` as `Ascension Launcher.exe` with a Windows PID (e.g. 212, 308).

**Wrapper path:** `cs_wrapper` logs `decoy_pid=<Windows PID>` and rewrites `--launcher-pid` to that value.

**Hang vs immediate exit:** Wrapper invocation hangs 30s+ with valid decoy PID (not immediate guard rejection).

---

## Token requirement

Sidecar CLI requires `--token` (one-time launcher identity). Strings include `"empty launcher token, exiting"`.

The token is generated by the live Electron launcher per handoff. The decoy provides PID/name survival only — it cannot participate in token attestation.

## Absence of HTTP connection attempts

**Control I:** Loopback listener pre-seeded with `api_base_url`; sidecar exited in ~0.46s with invalid PID or hung 30s+ via wrapper with **zero** HTTP connection attempts.

**Interpretation:** Sidecar blocks before outbound client HTTP. `url-file` is documented in sidecar CLI as the path where the sidecar **writes** its API base URL after binding — not a pre-seeded client endpoint.
